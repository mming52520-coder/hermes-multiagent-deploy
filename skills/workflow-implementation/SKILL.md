# 实现与根因修复

## 输入、工具与边界

读完整任务和 /handoff/researcher/artifacts/DESIGN.md。以任务的 Workflow round 判断是否存在前轮，不从需求中的“修复/修改”推断：round 0 没有 /handoff/repair；后续轮须读 /handoff/repair/result.json，再使用实际提供的失败日志、独立测试或审查报告。本轮明确的修改要求与原需求合并执行；旧设计和旧 PASS 不验证新要求。

使用启用的文件、搜索、终端和 web 工具。只在任务授权的候选中改代码，报告写 /output；本 skill 不改变挂载、网络、审批或提交权限。Builder 与 Tester 并行，首轮不等待 /handoff/tester 或 /handoff/platform；上一轮材料在 /handoff/repair，不猜未来角色的输出路径。

## 判断与实施

1. 确认实际候选目录、工作区状态、现有变更及当前验收条件；终端明确设置候选 workdir（容器别名 /candidate），避免在执行目录的父目录运行测试。
2. 从触发入口追踪调用链、共享实现、配置来源、错误传播和相关测试。修复任务先用现有测试或最小复现确认失败；功能任务先确认可复用实现及受影响调用方。
3. 优先现有代码、标准库及已有依赖。需要外部 API/协议信息时核对对应版本的一手来源；遵循任务的网络限制，不扩大授权。不以猜测的未来需求添加接口、配置或防御分支。
4. 修复造成已观察问题的原因，并覆盖受影响的同类路径；保留约束要求的兼容性、错误处理、安全和隔离。变更范围由需求及调用链证据决定。
5. 用行为测试验证新要求及受影响的旧行为。沿实际调用链检查需求输入域是否被中间转换、库默认限制或类型语义缩窄；对有此风险的路径选择能越过该限制的合法输入和独立预期值，不只照抄示例或做往返自洽检查。先运行针对性检查，并核对任务提供的固定项目命令的发现/导入方式；平台负责冻结候选后的完整命令与独立测试，除项目要求或具体失败外，不重复整个套件。
6. 完成前比较实际变更与本轮要求，检查新增未跟踪文件及源码 diff；测试成功只覆盖实际运行的场景，不代表遗漏要求也已完成。将每个验收项连接到实现路径与证据，缺口明确列出。

## 失败与停止

输入不足时核对任务和交接目录，不用不存在的路径补齐想象。关键设计缺失或要求冲突使实现无法确定时 kanban_block，给出具体缺项与继续条件；可独立确定的工作可先完成并说明范围。

工具拒绝或不可用时记录实际错误与未验证范围。列目录优先 search_files 或简单命令，减少不必要的脚本审批；不能靠更改审批、网络或挂载恢复。只有输入/环境已改变或存在合理替代时再试。测试失败应区分实现、测试夹具和环境，修复原因，不删除仍有效的断言。

## 交付与完成

按 SOUL 把持久实现报告写入 /output，并用 kanban_complete 提交已有字段：round_changed_files、verification（命令、cwd、实际结果）、findings、evidence_refs、residual_risks。记录哪些当前要求已验证、哪些未验证及原因；无改动的结论同样需要当前要求的证据。

由平台绑定不可变快照、累计 changed_files、执行完整测试并交 Reviewer。不要自己重造快照标识或宣称最终 ACCEPTED。独立测试失败或审查发现通过现有修复轮处理，不另起无授权的循环。
